# Финансовая модель ZalogHub — v0.1

Статус: модель для обсуждения. Не SQL-миграция и не подтверждение юридической применимости условий. Рабочая Prisma-схема не менялась. Область: сделки, договоры, банковские поступления и расчёт займов. Маркетплейс заявок и Telegram будут отдельным контуром.

## Как открыть

В https://app.diagrams.net/ выбрать «Устройство» и открыть finance-data-model.drawio. Пять вкладок содержат обзор и детальные связи. Файл finance-data-model.dbml предназначен для импорта в dbdiagram.io; он содержит те же таблицы и связи в текстовом виде. Не загружать на внешние сервисы реальные выписки и персональные данные: схема содержит только названия и типы полей.

Генератор: `python docs/architecture/build_finance_model.py`. Источник таблиц и связей находится в build_finance_model.py; drawio и DBML генерируются вместе. Проверены XML, уникальность идентификаторов и существование всех концов связей. Визуальная проверка в редакторе пока не выполнена; при ручной правке drawio повторная генерация перезапишет расположение блоков.

## Владение данными

- platform: пользователи, рабочие пространства, участники, сделки, договоры, документы, залоги, аудит.
- banking: подключения, счета, синхронизация, операции, версии операций, сопоставления, очередь исходящих сообщений.
- finance: расчётные счета договоров, версии условий и календарей, подтверждённые события, воспроизводимые расчёты и их результаты.

Это логическое разделение. На старте допустим один PostgreSQL с модулями/схемами и явными границами доступа. При отдельной БД финансового сервиса workspace_id, source_contract_id, source_document_ref и counterparty_ref остаются внешними ID, без FK к платформе. Пунктир на диаграмме означает внешнюю ссылку. financial_events.source_ref — строковый ID сообщения/сопоставления, не физический FK.

users — учётные записи сотрудников. parties — участники договоров (физлица, ИП, организации), которым не обязательно иметь доступ в приложение. workspaces — граница доступа и владения портфелем; роли задаются через workspace_members. Детальные реквизиты parties и аутентификация пользователей пока не развёрнуты. ИНН не уникален глобально для всех типов сторон: физлицо и ИП могут иметь один ИНН.

## Основные отношения

- workspace 1:N deals; deal 1:N contracts. Сделка объединяет документы и обязательства, но сама не является расчётным счётом.
- contract N:M parties через contract_parties: заёмщик, займодавец, поручитель и другие роли.
- contract N:M documents: основной текст, допсоглашения, уведомления, основания расходов.
- contract N:M collaterals. Один объект может обеспечивать несколько обязательств; учитываются приоритет и обеспечиваемая сумма. История оценки и собственники объектов — следующий этап модели.
- loan_account соответствует одному договору займа в одной валюте. Договоры залога и агентские договоры не обязаны создавать loan_account. Для нескольких самостоятельных обязательств/валют на один договор нужно снять это ограничение и добавить obligation_scope.
- loan_account 1:N terms_versions, financial_events, calculation_runs.
- terms_version 1:N term_rules. Каждая опубликованная версия — полный набор условий, а не частичный patch.
- bank_account 1:N bank_transactions; transaction 1:N revisions. Только подтверждённые сопоставления порождают финансовые события.
- calculation_run 1:N obligations, accrual_lines, payment_allocations; 1:0..1 loan_snapshot. Snapshot публикуется только для успешного расчёта.

## Банковский контур

Операция банка и её распределение по компонентам долга — разные сущности. transaction_matches связывает часть банковской операции с договором; payment_allocations показывает, как движок распределил подтверждённый платёж по обязательствам.

Выписка может приходить по API или из файла. bank_sync_runs хранит запрошенный период, статус, курсор и фактическую полноту данных. Частичная страница не означает завершённую синхронизацию. Формат credential_ref — ссылка на хранилище секретов, не токен в БД.

bank_transactions хранит стабильную идентичность операции. Направление, сумма, валюта, даты, статус и назначение находятся в неизменяемых bank_transaction_revisions. Исправление банка создаёт новую revision, сохраняя прежние наблюдения и исходный payload. Источником подтверждения служит конкретная revision, а не изменяемая строка операции.

Если банк не предоставляет устойчивый ID, адаптер формирует его по документированному алгоритму с выявлением коллизий; назначение и сумма сами по себе не гарантируют уникальность.

transaction_matches.status: proposed / confirmed / rejected / superseded. Смена подтверждённого сопоставления не удаляет старое: новое ссылается на supersedes_id, прежнее финансовое событие сторнируется, создаётся новое. Несколько договоров на один перевод поддерживаются несколькими matches. Несколько переводов в один договор поддерживаются аналогично.

## Договорные условия

terms_versions.contract_amount — договорная сумма, а не фактически выданный остаток. Основной долг возникает из подтверждённых событий выдачи, в том числе переводов третьим лицам по поручению. Допсоглашение само по себе не является фактом перечисления денег.

term_rules.kind: interest / schedule / penalty / allocation / prepayment / rate_transition. definition — JSON строго определённой версионируемой схемы. Никакого произвольного JavaScript/SQL из договора. Неизвестный тип правила запрещает окончательный расчёт.

Профиль ваших договоров должен выразить: льготную/стандартную месячную ставку, утрату льготы, перерасчёт с месяца нарушения, фактические дни, ежемесячные проценты и тело в конце срока, ступенчатую пеню, особую очередность просроченного платежа, ограничения досрочного возврата и уведомления. Параметры каждого правила ссылаются на конкретный пункт и источник.

Перед реализацией необходимо согласовать: дневной эквивалент месячной ставки; включение граничных дней; перенос выходных; поведение при частичном платеже; базу пени; ретроактивность повышенной пени; порядок начисления и оплаты в один день; пределы начислений; расчёт досрочного погашения. Записанное в договоре правило и подтверждение его применимости — разные вопросы.

effective_on — с какого дня действуют условия; recorded_at — когда они приняты системой. Исправление создаёт новую версию. При расчёте сначала ограничивается набор известных версий по knowledge_cutoff, затем для каждой даты выбирается применимая версия по effective_on и version_no. Задним числом принятое соглашение должно менять только новые расчёты, не историю ранее выпущенных результатов.

calendar_versions и calendar_days неизменяемы после публикации. Календарь должен покрывать весь расчётный и прогнозируемый период; отсутствие дня является ошибкой, а не выходным по умолчанию.

## События и расчёт

financial_events — неизменяемые факты: disbursement, receipt, reversal, expense, waiver, notice, settlement. payload имеет отдельную схему на каждый kind. Выдачи и поступления содержат положительную amount, направление задаёт kind. Денежное сторно ссылается на оригинал и компенсирует его ровно один раз; частичная отмена требует отдельного согласованного типа события. Неденежные события могут иметь amount = NULL. Прекращение обязательства через отступное требует принятого факта/документа, а не автоматического вывода из размера долга.

effective_on — финансовая дата; recorded_at — дата получения; sequence_no — однозначная последовательность принятия в пределах займа. Порядок обработки событий одного дня дополнительно задаётся версией алгоритма/правилами. Платёж может быть загружен сегодня, но влиять на вчерашний расчёт. Нельзя вычислять долг просто от остатка последней выписки.

Каждый calculation_run фиксирует as_of_on, knowledge_cutoff, engine_version и input_hash. calculation_inputs перечисляет точные ID и хеши всех событий, условий и календарей; input_ref — проверяемая сервисом полиморфная ссылка. Это позволяет повторить расчёт независимо от последующих загрузок. Прошлый run не перезаписывается; supersedes_run_id связывает новые результаты с заменяемыми.

obligations — требования с датой оплаты и устойчивым obligation_key. accrual_lines — подробности формулы. payment_allocations — применение денег к конкретным требованиям. Эти три таблицы являются производными и всегда читаются в рамках одного run. Их нельзя смешивать между версиями расчёта.

loan_snapshots различает весь остаток тела, неоплаченные начисления, сумму к оплате сейчас, просроченную сумму и нераспределённую переплату. due_total уже включает overdue_total. Просрочка не равна всему остатку тела. payoff_amount не публикуется, если условия/события для него неоднозначны; причина содержится в diagnostics. next_payment_* отсутствуют при полном прекращении обязательств.

Актуальность расчёта и полнота банковских данных различаются. API платформы должно рядом с run показывать complete_through по задействованным счетам и наличие нераспределённых операций. Дневное начисление запускается календарём даже без банковских поступлений. Сам движок может принимать такой же стандартизированный набор фактов и из другого источника.

## Обязательные ограничения реализации

DBML — логическая модель, не полное описание SQL CHECK и политик доступа. Перед миграцией добавить:

1. Workspace isolation: составные FK/проверки и RLS или эквивалент. Нельзя связать договор одного workspace со стороной, залогом или счётом другого. loan_accounts получают внешний workspace ID с проверкой авторизации на границе сервиса.
2. Внутренние связи банков: sync_run.account должен принадлежать той же connection, что указана в run. revision должна соответствовать счёту sync_run.
3. Денежные суммы операций и matches положительны; валюта matches и финансового события совпадает с валютой займа. Конвертация валют в v0.1 не поддерживается.
4. Сумма действующих подтверждённых matches не превышает сумму принятой revision операции. Конкурентное подтверждение выполняется с блокировкой операции/транзакционной сериализацией. Статусы superseded не участвуют в сумме.
5. Для финансовых событий уникален (loan_account_id, idempotency_key). Повторная доставка не создаёт второй платёж. Повтор с другим содержимым под тем же ключом — ошибка. Сторно не может ссылаться на чужой заём или на себя; запрещено повторное полное сторно оригинала.
6. allocation.run_id = obligation.run_id; события, обязательства, правила и версия условий принадлежат тому же loan_account. accrual.rule и obligation.terms_version должны быть согласованы для периода. Сумма распределений не превышает доступную сумму поступления; переплата учитывается отдельно.
7. Опубликованные terms/rules/calendars, принятые события и завершённые runs неизменяемы. FK RESTRICT и архивирование вместо каскадного удаления финансовой истории. Хеши фиксируют каноническое представление JSON.
8. Decimal/integer arithmetic; никаких float для денег. Ставки хранятся долями: 0.04 = 4%, единица периода задаётся rule/rate_unit. Правила округления фиксируются в условиях; промежуточная точность выбирается по максимальным поддерживаемым суммам/срокам.
9. outbox записывается атомарно с подтверждением match. Изменение match порождает сторно/замену через outbox. Доставка at-least-once, обработка идемпотентная. В отдельном сервисе с собственной публикацией нужна своя outbox.
10. Выплата наличными, зачёт, судебное изменение и списание допускаются только как типизированные подтверждённые события с основанием и аудитом. Банковское назначение не определяет автоматически юридическую природу операции.

## Связь с текущей Prisma-моделью

User сохраняется; отношения по userId переходят к workspace с начальным workspace для каждого текущего владельца. Borrower становится party с ролью borrower; Deal остаётся контейнером сделки. Условия займа выносятся из Deal в Contract + LoanAccount + TermsVersion + TermRule. Collateral связывается с договорами через таблицу N:M. Disbursement переносится как подтверждённое событие выдачи. Payment — как факт поступления, а его type сохраняется в legacy metadata для сверки; нельзя без проверки трактовать его как результат нового распределения. Перенос требует сравнения расчётов и подтверждения полноты истории; автоматическая миграция в этой работе не выполнялась.

## Очередность реализации

1. Согласовать правила вашего договорного профиля и контрольные примеры с датами/ожидаемыми суммами.
2. Реализовать типизированные условия, события и детерминированное ядро; проверить ретроактивные изменения и сторно.
3. Подключить ручной импорт выписки, сверку и объяснимое распределение платежей.
4. Подключать Альфу, Т-Банк и Сбер через одинаковый входной контракт.
5. Расширять набор поддерживаемых договорных профилей без изменения банковских адаптеров.
