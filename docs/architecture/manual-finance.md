# Ручной финансовый учёт

## Что подключено

В приложении остаётся одна БД. Чистая функция `calculateLoan(input)` находится в
`apps/api/src/finance/core/loan/calculate-loan.ts`. Она не импортирует Nest или Prisma.
Адаптер `apps/api/src/finance/deal-finance.ts` переводит существующие выдачи и
поступления сделки в стандартизированные события. `DealsService` загружает факты,
вызывает функцию и возвращает результат контроллеру.

Сейчас источники фактов — `disbursements`, `payments` и согласованные действия
`finance_instructions`. Календарь использует `calendar_versions` и `calendar_days`.
Таблицы финансового фундамента `financial_events`, `calculation_runs`, `obligations`
ещё не заполняются этим контуром. Не следует читать их как актуальный
финансовый учёт сделки. Распределения и начисления пока вычисляются при запросе.

## Один расчёт

1. Проверить условия, события, диапазон дат и рабочий календарь.
2. Отфильтровать будущие операции и отсортировать факты по дате и sequenceNo.
3. Воспроизвести дни: закрыть истёкший процентный период, начислить пени,
   применить операции, начислить проценты на оставшееся тело.
4. Ранняя оплата может закрыть прогноз текущего процентного периода. Ещё не
   начавшиеся периоды не оплачиваются. При досрочном возврате тела прогноз
   уменьшается; высвободившаяся переплата относится в удержанный остаток того же платежа.
5. Если обнаружена утрата льготы или ретроактивное повышение пени, повторить
   историю с уточнёнными ставками. Пересчитываются также распределения платежей.
6. Вернуть фактический долг, прогноз графика, распределения каждого поступления
   и дневные строки начислений. Повторный вызов ничего не записывает и не удваивает.

В этом профиле день выдачи включён в начисление. Погашение тела действует до
начисления процентов дня оплаты. Процентный период `[fromOn, dueOn)` не включает
срок оплаты. Просрочка начинается на следующий день. День оплаты может включаться
или исключаться из пени параметром `penalty.paymentDay`.

`FIXED_30_DAYS` означает реальное число дней / 30: 31 день при 4% даст
4% × 31 / 30. Фиксированная сумма ровно 4% за любой календарный месяц здесь не используется.

## Условия и подтверждение

`Deal.financeTerms` содержит JSON типа `LoanTerms`, версия схемы 1. Это действующий
профиль расчёта; старые плоские поля сделки используются для заготовки. После
подтверждения их финансовое изменение через обычный PATCH блокируется. Изменять
профиль следует через PUT финансовых условий. Старый и новый JSON сохраняются в
неизменяемом `audit_entries`; это история конфигурации, не автоматический механизм
вступления дополнительных соглашений в определённую дату.

Для существующих сделок профиль автоматически не утверждается. GET возвращает
`CONFIGURATION_REQUIRED`, пока профиль не сохранён. Это позволяет не назначать
неописанные ранее правила задним числом по одному лишь набору ставок.

Заготовка `suggestedTerms` использует льготную ставку, обычную пеню, делитель 30,
удержание остатка, блокировку обычного досрочного тела и согласованное закрытие.
**Она не является полным профилем стандартного договора:** утрату льготы и
ретроактивное повышение пени нужно задать явно.

Для присланного договора в профиль дополнительно входят:

- `rateLoss.standardRate = "0.07"`;
- `rateLoss.graceWorkingDays = 5`;
- `rateLoss.partialPaymentTriggers = true`;
- `rateLoss.retrospective = "DUE_MONTH"`;
- `penalty.base = "CONTRACT_AMOUNT"`, `dailyRate = "0.005"`;
- `penalty.increase = { afterMonths: 3, dailyRate: "0.015", retrospective: true }`.

Рабочий календарь передаётся как `{fromOn, toOn, workingDays}`. Внутри объявленного
покрытия отсутствующая дата считается нерабочей. Нужно передать все рабочие даты,
включая рабочие субботы, и учесть праздники и переносы. Покрытие обязано включать
период от начала займа до даты расчёта. При неполном покрытии расчёт прекращается
с ошибкой. Обычная пятидневка автоматически не подставляется. При подготовке
профиля сервер импортирует календарь РФ из XMLCalendar и закрепляет его версии.

Для судебного эталона ставка 7% уже определена исходным расчётом. Новый движок
воспроизводит проценты 389993.45, пени 2299194.81 и общий долг 3504505.57.
Стартовая выдача эталона — агрегированная позиция на начало судебного периода,
а не восстановленная банковская история.

## API

Все маршруты требуют JWT и проверяют владельца сделки.

| Маршрут | Назначение |
| --- | --- |
| GET /deals/:id/finance/terms | Текущие условия, заготовка и история изменений условий |
| POST /deals/:id/finance/terms/preview | Нормализованные условия, описание и confirmationHash |
| PUT /deals/:id/finance/terms | Сохранить terms и confirmationHash из preview |
| GET /deals/:id/finance?asOfOn=2026-01-28 | Пересчитать из истории на заданную дату |
| POST /deals/:id/payments | Зарегистрировать поступление и вернуть обновлённый расчёт |
| POST /deals/:id/disbursements | Зарегистрировать выдачу и вернуть обновлённый расчёт |
| DELETE /deals/:id/payments/:operationId | Отменить поступление с сохранением записи и пересчитать |
| DELETE /deals/:id/disbursements/:operationId | Отменить выдачу с сохранением записи и пересчитать |

Тело ручного поступления:

```json
{
  "amount": "26000.00",
  "date": "2026-01-25",
  "comment": "Частичная оплата",
  "idempotencyKey": "748939da-e9cb-4921-a69e-088d4e6350cd"
}
```

`amount` предпочтительно передавать строкой, максимум 16 цифр до точки и 2 после.
Небольшие JSON-числа ещё принимаются для совместимости. Дата — существующая
календарная дата без времени; будущие фактические операции запрещены.
Старое поле `type` необязательно и не влияет на расчёт. Новые поступления имеют
служебное legacy-значение OTHER; действительное распределение находится в `finance`.

При повторе того же ключа с теми же данными возвращается существующая операция.
Изменение суммы, даты, комментария или повтор ключа отменённой операции даёт 409.
Ключ ограничен сделкой и видом операции. Клиент сохраняет ключ при повторной
попытке той же отправки. Для нового факта нужен новый ключ.

Блокировка строки сделки сериализует конкурентные операции. Факт, аудит и проверка
пересчёта находятся в одной транзакции. Ошибка проверки откатывает запись. При
банковской интеграции внешний inbox должен отдельно сохранять доставленное событие
и обеспечивать повтор обработки, в том числе при недоступном календаре.

## Значения результата

- `totalOutstanding` — тело + фактически начисленные непогашенные проценты + пени.
  Будущие проценты в него не входят.
- `snapshot.dueNow` — обязательства со сроком сегодня и ранее.
- `snapshot.overdueTotal` — непогашенная часть со сроком строго раньше даты расчёта.
- `snapshot.nextPaymentOn/Amount` — ближайший будущий непогашенный платёж.
  Это прогноз при текущем теле и уже определённой ставке; будущие нарушения
  ещё не предполагаются, текущая просрочка показана отдельно.
- `prepaidInterest` — часть ранней оплаты сверх уже начисленных процентов.
- `unappliedCredit` — удержанный остаток поступлений. При HOLD он автоматически
  не расходуется в будущие даты. Он может сосуществовать с новым долгом.
- `payments` — история применения каждого поступления, `allocations` — её детализация,
  `accruals` — объяснение начислений по дням.

В карточке сделки подключены эти показатели и детализация распределения.
Редактор профиля договора и загрузка календаря через интерфейс ещё не добавлены:
на текущем этапе условия настраиваются через API.

## Что ещё не выражено этим профилем

Уведомления, досрочное истребование, отступное, расходы, списания, перенос сроков
на рабочий день и изменения условий с будущей датой вступления требуют следующих
правил/типов событий. Возвраты переплаты, согласованные зачёты и закрытие во время
моратория реализованы отдельными распоряжениями; автоматического зачёта нет.
Универсальность означает независимость расчёта от банка и способа хранения;
поддержку любого произвольного текста договора этот профиль не обещает.

Прежний `calculateFinance` остаётся низкоуровневым калькулятором с собственным
ограничением на пени с поступлениями. Ручной контур вызывает новый `calculateLoan`,
который рассчитывает их вместе по истории обязательств.

## Проверка

```powershell
pnpm --dir apps/api test:finance
pnpm --dir apps/api build
pnpm --dir apps/web build
```

Реальные тесты БД требуют явно указанного `TEST_DATABASE_URL` на локальную
`zaloghub_migration_test`. Они создают случайную схему, применяют все миграции,
проверяют сервис с ядром и удаляют только свою схему. Рабочая БД не используется.

```powershell
$env:TEST_DATABASE_URL = '<URL локальной zaloghub_migration_test>'
pnpm --dir apps/api test:finance:db
pnpm --dir apps/api test:db
```

Подробный API новых сценариев: [настройка, календарь и согласованные действия](finance-workflows.md).

На другом окружении перед запуском приложения:

```powershell
pnpm --dir apps/api db:migrate
pnpm --dir apps/api db:generate
```
