# Настройка договора, календарь РФ и согласованные действия

Этот этап реализует backend. Интерфейс настройки и управления действиями, а также
полноценная история операций — следующие этапы. Все маршруты защищены JWT;
маршруты сделки проверяют её владельца. Деньги передаются строками, даты — YYYY-MM-DD.

## Настройка финансовых условий

1. `GET /deals/:id/finance/terms`: текущий профиль, заготовка, описание и аудит.
2. `POST /deals/:id/finance/terms/preview` с `{ "terms": ... }`: проверить профиль,
   подготовить календарь и вернуть нормализованные `terms`, читаемое `description`,
   пробный `finance` и `confirmationHash`.
3. `PUT /deals/:id/finance/terms` с `terms` и `confirmationHash` из preview.
   Изменение параметров после просмотра требует нового preview.

Профиль `LoanTerms` содержит ставки, график, округление, базу пени, её повышение,
правило потери льготы, мораторий и условия согласованного закрытия. Описание прямо
указывает делитель 30/календарный месяц, включение дня оплаты в пени и отсутствие
автоматического переноса срока платежа на рабочий день.

Для моратория с минимумом процентов за шесть месяцев при 48% номинальных годовых:

```json
{
  "principalRepaymentFromOn": "2026-07-10",
  "settlement": {
    "minimumInterestRate": "0.04",
    "minimumInterestMonths": 6
  }
}
```

Это фрагмент полного LoanTerms. Процентная ставка здесь месячная, долями единицы.
Минимальная сумма процентов = сумма договора × ставка × месяцы. Уже оплаченные
проценты засчитываются. Если фактически начислено больше минимума, применяется
фактически начисленная сумма. Неуплаченные пени добавляются отдельно.

`allocation.earlyPrincipal = BLOCKED` запрещает обычному поступлению погашать
будущее тело. До `principalRepaymentFromOn` мораторий блокирует обычное тело также
при ALLOWED. Согласованное закрытие является отдельным исключением с проверкой
минимальных процентов; перевод денег сам по себе такого разрешения не создаёт.

## Российский производственный календарь

Источник — [репозиторий XMLCalendar](https://github.com/xmlcalendar/data), путь
`ru/{year}/calendar.xml`. Резерв — JSON того же проекта на xmlcalendar.ru.
Оба источника преобразуются в полный набор дат: WORKING, DAY_OFF, SHORTENED.
Сокращённый день считается одним рабочим днём при подсчёте пяти рабочих дней.
Учитываются рабочие субботы, федеральные праздники и перенесённые выходные.
Это федеральный календарь пятидневной недели, без региональных дополнительных праздников.

Проверки включают все даты года, типы исключений, обязательные федеральные
праздники и разумное число рабочих дней. Отсутствующий год или невалидный ответ
дают ошибку, а не замену обычными понедельниками–пятницами.

Нормализованные данные сохраняются в `calendar_versions` и `calendar_days`.
Хеш определяет версию; повтор той же версии не дублирует записи. Публикация
выполняется после сохранения полного года. Опубликованные версии защищены от
изменения триггерами БД. При изменении источника появляется другая версия.
URL фактически использованного источника и время импорта сохраняются.

Профиль сделки хранит `calendarVersionIds` и нормализованный снимок рабочих дней.
Он не меняется при обновлении источника. В preview календарь для rateLoss
подготавливается сервером; вручную перечислять дни во фронтенде не требуется.

| Маршрут | Назначение |
| --- | --- |
| GET /finance/calendars/ru | Опубликованные версии и их происхождение |
| POST /finance/calendars/ru/import | `{ "year": 2026, "refresh": true }`: импорт или проверка новой версии |
| POST /deals/:id/finance/terms/calendar/extend | `{ "asOfOn": "2027-12-31" }`: расширить покрытие, сохранив закреплённые версии прежних лет |

Без asOfOn расширение идёт до текущей даты. Допускаются доступные годы начиная с
2013, максимум следующий календарный год относительно сервера. Наличие данных
будущих лет не предполагается: источник должен действительно их опубликовать.
Расширение сохраняется в аудите как изменение профиля. Фоновая задача обновления
не запускается: импорт и расширение доступны явно через API, а отсутствующие годы
автоматически импортируются при подготовке нового профиля.

Реальные тестовые данные 2025–2026 сохранены рядом с парсером. Проверяются рабочая
суббота 01.11.2025, выходной 03.11.2025, праздники и переносы 2026 года. Для сверки:
[постановление о переносах 2026](https://static.government.ru/media/files/4jeB8hNKm69ggOa9yDiYOli6YoAyM21i.pdf).

## Переплата: возврат — основной вариант

`GET /deals/:id/finance/credits` возвращает остатки по исходным поступлениям:

- `remainingAmount` — остаток после распределений и подтверждённых возвратов;
- `reservedForRefund` — запрошен возврат, фактическое исполнение ещё не подтверждено;
- `reservedForFuture` — согласован целевой зачёт будущих процентов;
- `availableAmount` — свободная сумма для нового решения;
- `preferredAction = REFUND` — основной вариант для интерфейса.

Возврат:

1. `POST /deals/:id/finance/credits/refunds`:

```json
{
  "receiptId": "UUID исходного поступления",
  "amount": "7350.00",
  "date": "2026-01-21",
  "idempotencyKey": "UUID запроса"
}
```

2. Деньги зарезервированы, банковского перевода пока нет.
3. После фактического перевода:
   `POST /deals/:id/finance/credits/refunds/:instructionId/confirm`
   с `{ "date": "2026-01-22", "transferReference": "номер/ссылка на перевод" }`.
4. До исполнения запрос можно отменить через `/cancel` с `{ "date": "..." }`.

Сумма должна быть свободным остатком именно указанного поступления. Возврат
не уменьшает тело или оплаченные проценты. Он не уменьшает gross receivedTotal:
отдельно растёт refundedTotal. Баланс:

`поступления = распределено + фактически возвращено + оставшийся остаток`.

## Согласованный зачёт

`POST /deals/:id/finance/credits/preview` принимает receiptId, amount и date.
Сервер предлагает разбивку по будущим процентным периодам, учитывая уже
согласованные резервы; превышение доступного графика остаётся к возврату.
Предложение ничего не записывает и не применяет.

Для согласования `POST /deals/:id/finance/credits/agreements`:

```json
{
  "receiptId": "UUID поступления",
  "date": "2026-01-21",
  "idempotencyKey": "UUID запроса",
  "agreementReference": "Ссылка на согласование с заёмщиком",
  "targets": [
    { "obligationKey": "interest:2026-02-25", "amount": "7350.00" }
  ]
}
```

До начала периода сумма является целевым резервом. При начале периода она
применяется из того же поступления, без создания нового денежного поступления.
Неровная сумма частично покрывает последний выбранный период. Если обязательство
стало меньше, высвободившаяся часть возвращается в свободный остаток.
Ещё не применённое соглашение отменяется через
`POST .../credits/agreements/:instructionId/cancel` с date.
Применённый зачёт этим действием не отменяется.

## Согласованное полное закрытие

1. `GET /deals/:id/finance/settlements/quote?date=2026-01-20` возвращает расчёт
   на конец выбранного дня: тело, фактические проценты, минимум за мораторий,
   оплаченные проценты, пени, имеющиеся средства, дополнительную сумму к переводу,
   quoteHash и liabilityHash.
2. `POST /deals/:id/finance/settlements`:
   `{date, quoteHash, idempotencyKey, agreementReference}` фиксирует соглашение.
   Оно само не закрывает займ и не создаёт деньги.
3. Реальные поступления регистрируются обычным `/payments`.
4. `POST .../settlements/:instructionId/execute` с `{date}` проверяет дату,
   актуальность обязательств и наличие денег. Затем направляет средства на
   закрытие процентов, пени и тела. Сделка получает CLOSED.
5. Неисполненное соглашение можно отменить через `/cancel` с date.

Пример: тело 1 млн, минимум 4% × 6 = 240 тыс. Без предыдущих оплат нужно
1.24 млн. При ранее оплаченных 80 тыс. процентов — 1.16 млн, плюс имеющиеся
непогашенные пени/проценты сверх минимума при их наличии.

Оплата в дату закрытия учитывается на конец дня. Выполнение возвращает
будущие процентные предоплаты к фактической/минимальной сумме, освобождает
неиспользованные будущие резервы и прекращает дальнейшие начисления на тело.
Резервы запрошенных возвратов сохраняются и для закрытия не расходуются.

quoteHash защищает согласование конкретного предложения. При исполнении проверяется
liabilityHash: новые деньги могут покрыть соглашение, но изменение условий или
самих начисленных обязательств требует нового согласования.

## Хранение и безопасность повторов

`finance_instructions` хранит неизменяемое содержание распоряжения, ссылку на
согласование, даты и состояние AGREED / EXECUTED / CANCELLED. Удаление и изменение
содержания запрещены триггером; допускается одно завершение AGREED. Подтверждение
возврата хранит executionReference. Переходы дополнительно записываются в аудит.

Все изменения сериализуются блокировкой сделки; запись и пересчёт выполняются
в одной транзакции. Повтор ключа с другим содержанием даёт 409. Параллельные
запросы не могут использовать один остаток дважды. Подтверждённые возвраты и
согласованные резервы защищены от поглощения ретроактивным перераспределением
первоначального поступления; образовавшийся договорной долг показывается отдельно.

Существующие низкоуровневые калькуляторы остаются совместимыми. Новая хронология
принимает нормализованные `actions` отдельно от денежных `events`; будущая банковская
интеграция регистрирует факты, а согласования остаются действиями инвестора.

## Черновой интерфейс карточки сделки

Блок «Управление займом» подключён к перечисленным API без дублирования
денежных расчётов в браузере. Используется существующая стилизация Ant Design.

- «Условия договора»: редактирование правил, серверный предварительный расчёт,
  описание и явное подтверждение перед сохранением. Здесь же доступны импорт
  российского календаря и расширение покрытия договора.
- «Переплата и возвраты»: остатки по поступлениям, запрос возврата, отдельное
  подтверждение уже выполненного перевода, предварительная разбивка и
  согласование зачёта будущих процентов. Неисполненные решения можно отменить,
  если их средства ещё не использованы.
- «Закрытие займа»: расчёт на выбранную дату, фиксация согласования,
  исполнение после добавления фактического поступления и отмена соглашения.

Обычный путь проверки: настроить условия → проверить описание → сохранить →
добавить платёж → проверить распределение и следующий платёж → распорядиться
переплатой. Закрытие выполняется отдельным согласованным действием.

Для сделки с сохранёнными финансовыми условиями общая форма редактирования
не изменяет старые поля ставок и дат: правила редактируются в финансовой форме.
Полная объединённая история начислений и перерасчётов остаётся следующим этапом.

Код интерфейса разделён на `entities/deal/api/financeApi.ts`, типы
`entities/deal/model/finance.types.ts` и компоненты `features/deal-finance`.

Проверка 06.11.2026: браузер, настоящий API и отдельная временная БД с
вымышленными данными. Займ 1 000 000 ₽ под 4%/мес., выдача 1 ноября,
первый срок 25 ноября: предварительный платёж 32 000 ₽. Внесение 39 350 ₽
закрыло первый период и оставило 7 350 ₽. Согласован зачёт 1 000 ₽,
запрошен и подтверждён возврат 6 350 ₽. Расчёт закрытия при минимуме
4% × 6 месяцев показал 1 207 000 ₽ к дополнительному внесению; после
внесения и исполнения соглашения тело и долг стали нулевыми, статус — CLOSED.
