# Проверки заёмщика: хранение данных

Миграция: `20261113000000_borrower_verifications`. Контроллеры, OCR и внешние интеграции добавляются следующим этапом. Миграция не создаёт фиктивных результатов и не запускает внешние проверки.

Backend реализован следующим этапом: [маршруты, форматы запросов и обработка задач](borrower-verifications-api.md). Автоматические источники и OCR пока не подключены. Дополнительная миграция `20261113010000_verification_review_status` добавляет статус пункта AWAITING_REVIEW перед явным принятием результата.

## Таблицы и существующие связи

| Prisma | PostgreSQL | Назначение |
| --- | --- | --- |
| `PartyIdentityVersion` | `party_identity_versions` | Неизменяемая подтверждённая версия ФИО, паспорта, адресов и идентификаторов |
| `BorrowerVerification` | `borrower_verifications` | Эпизод проверки человека, выбранная версия данных, решение |
| `BorrowerVerificationItem` | `borrower_verification_items` | Снимок пункта чек-листа, схема результата, источник, принятый запуск |
| `BorrowerCheckRun` | `borrower_check_runs` | Ручной или автоматический запуск, снимок входа, результат, ошибка и очередь |
| `BorrowerCheckFinding` | `borrower_check_findings` | Конкретное дело, производство, сообщение или совпадение |
| `BorrowerVerificationEvidence` | `borrower_verification_evidence` | Документы, ссылки, OCR и проверка доказательств |
| `BorrowerVerificationRisk` | `borrower_verification_risks` | Обоснование риска, критичность и устранение |

Проверяемый субъект — существующий `Party` вида PERSON или ENTREPRENEUR. Существующий `Borrower` используется через `Party.legacyBorrowerId`. Привязка к `Deal` необязательна. Новый дубликат таблиц людей, файлов или аудита не создаётся.

У `Document` добавлены `originalFilename?`, `sizeBytes?` и `createdAt`. Старые записи сохраняются; их дата `createdAt` заполняется временем миграции, а не неизвестной датой первоначальной загрузки. Файлы хранятся по существующему `storageKey`, содержимое не копируется в таблицы проверок. Персональные номера хранятся строками, даты документов — DATE, моменты событий — TIMESTAMPTZ(3), суммы — NUMERIC(20,2).

## Изоляция и целостность

У новых таблиц обязательный `workspaceId`. Составные FK запрещают смешивать рабочие пространства, проверки, пункты, запуски и найденные записи. Версия личности проверки принадлежит тому же Party; предшествующая версия — тому же человеку с меньшим номером. Акторы связаны с `User`; проверка их членства и полномочий остаётся обязанностью backend.

В дочерних таблицах `verificationId` намеренно продублирован: он позволяет обеспечить принадлежность всей цепочки составными FK и блокировать родительскую проверку при записи. У доказательства `runId` требует `itemId`, а `findingId` требует `runId`. Доказательство устранения риска принадлежит той же проверке.

Уникальны номер версии человека, код пункта в проверке, номер попытки и ключ идемпотентности в пункте, ключ найденной записи в запуске. SQL expression-index устраняет дубли риска по запуску, коду, версии правила и находке, включая риски без находки. Этот индекс, CHECK и триггеры не представлены полностью в Prisma: применять изменения только миграциями, не `db push`.

## Протокол записи для будущего backend

1. Создать DRAFT-проверку и снимки пунктов одной транзакцией. Неподтверждённое OCR хранить в evidence; подтверждение создаёт `PartyIdentityVersion` и связывает её с проверкой. Внешняя интеграция не требуется для ручного ввода.
2. До запуска проверить обязательные входные поля по `inputSchema` и полномочия пользователя. Создать QUEUED/RUNNING-запуск с `identityVersionId`, точным `inputSnapshot`, SHA-256 `inputHash`, версией правил и ключом идемпотентности. Без подтверждённой версии личности запуск запрещён.
3. Внешние запросы выполнять за пределами транзакции. В короткой транзакции записать findings и evidence, затем перевести run в SUCCEEDED/FAILED/CANCELLED. Ручной результат проходит тот же протокол: сначала RUNNING, дочерние строки, затем SUCCEEDED. Для MANUAL обязателен исполнитель.
4. При успехе для BOOLEAN требуется ненулевой ответ (false допустим), для CATEGORY — непустая категория, для MONEY — сумма с валютой, для DOCUMENT — приложенный документ пункта. RECORD_LIST может быть пустым. Backend валидирует полную структуру по `resultSchema` и не принимает отсутствие ответа источника за отсутствие рисков.
5. FAILED/CANCELLED не могут содержать положительный или отрицательный скалярный результат и оценку риска; FAILED требует код ошибки. Сохранять диагностические подробности без персональных данных в обычных логах.
6. После разбора совпадений выбрать `acceptedRunId`, перевести пункт в COMPLETED. SQL проверяет принадлежность, успех, текущую версию личности и срок актуальности. При смене версии личности принятые пункты автоматически становятся STALE. Проверку зависимости конкретных полей и повторных запросов реализует backend.
7. При завершении проверки передать решение, его автора, время и общую оценку риска. Все обязательные пункты должны быть COMPLETED/NOT_APPLICABLE, результаты — актуальными; QUEUED/RUNNING задач быть не должно. NOT_APPLICABLE требует причины. APPROVED_WITH_CONDITIONS требует условий, APPROVED запрещён при открытых рисках принятых запусков.
8. Обновления и аудит выполнять одной транзакцией. Повторная проверка после финализации создаёт новую запись с `previousVerificationId`.

Оценка риска отделена от фактов и решения менеджера. Общий итог и полнота схемы результатов вычисляются backend. CHECK не заменяет правила идентификации, проверку подлинности документов или юридическую оценку.

## История

- Подтверждённая версия личности не изменяется и не удаляется.
- Определение пункта, входные данные запуска и источник evidence после создания не заменяются.
- Факты завершённого запуска и его находок не изменяются. До финализации проверки допускается отдельное подтверждение запуска, оценка риска и разбор принадлежности находки человеку.
- Основание риска неизменно; разрешены действия по устранению и отклонению. RESOLVED требует доказательства, автора, даты и пояснения; DISMISSED — автора, даты и пояснения.
- COMPLETED/CANCELLED-проверка и все её дочерние записи заморожены. Перед CANCELLED нужно завершить/отменить фоновые задачи.
- DELETE новых исторических записей запрещён. Ссылки на существующие сущности используют RESTRICT. Политику регламентного удаления/обезличивания данных нужно проектировать отдельно; обычный CRUD не должен обходить защиту истории.

## Очередь автоматических проверок

Поля `availableAt`, `leaseOwner`, `leaseExpiresAt`, `heartbeatAt` подготовлены для PostgreSQL-worker. Захват QUEUED-задач: `SELECT ... FOR UPDATE SKIP LOCKED`, затем RUNNING с lease в той же короткой транзакции. При завершении lease очищается. Heartbeat и восстановление просроченных задач реализуются в worker, сама миграция задач не исполняет.

При записи дочерних данных триггер блокирует строку проверки: финализация сериализуется с записью результатов. Для сервисов использовать короткие транзакции READ COMMITTED; при конфликтах/взаимоблокировках повторять транзакцию целиком. При нескольких изменениях одной проверки сервис сначала блокирует её строку, затем изменяет дочерние записи; сетевые запросы под блокировкой не выполнять.

## Проверка миграции

```powershell
pnpm --dir apps/api db:validate
pnpm --dir apps/api db:generate
pnpm --dir apps/api test:borrower-verifications:db
pnpm --dir apps/api test:db
pnpm build:api
```

Интеграционный тест требует явно заданный `TEST_DATABASE_URL` с localhost/127.0.0.1 и базой `zaloghub_migration_test`. Не читает `.env`, не использует `DATABASE_URL`; создаёт и удаляет только собственную случайную схему. Проверяет обновление заполненной прежней схемы, сохранность существующих данных, межпространственные и внутренние FK, идемпотентность, историю, актуальность, доказательства, завершение и конкурентный захват задач. Подключён к CI отдельным шагом.
