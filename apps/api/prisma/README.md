# База данных: финансовая основа, этап 1

Приложение остаётся монолитом NestJS с одной PostgreSQL. Схема описана в `schema.prisma`, история изменений — в `migrations/`. Первая новая миграция: `20261105000000_financial_foundation`.

## Что реализовано

Добавлена 21 таблица из согласованной логической модели:

| Контур | Таблицы |
| --- | --- |
| Владение и доступ | `workspaces`, `workspace_members` |
| Участники | `parties` |
| Договоры | `contracts`, `contract_parties` |
| Файлы и обеспечение | `documents`, `contract_documents`, `contract_collaterals` |
| Расчётные условия | `loan_accounts`, `calendar_versions`, `calendar_days`, `terms_versions`, `term_rules` |
| Финансовая история | `financial_events` |
| Результаты | `calculation_runs`, `calculation_inputs`, `obligations`, `accrual_lines`, `payment_allocations`, `loan_snapshots` |
| Аудит | `audit_entries` |

`users`, `borrowers`, `collaterals`, `deals`, `payments`, `disbursements` и `auth_challenges` сохранены. Банковские подключения/операции и outbox намеренно отложены до соответствующего backend-модуля. Маркетплейс заявок также не входит в эту миграцию.

## Переход без поломки текущего API

Для каждого существующего пользователя создаются личный workspace и членство OWNER. К старым сделкам, заёмщикам и залогам добавляется `workspaceId`, существующие записи заполняются по `userId`. При регистрации нового пользователя личный кабинет создаёт триггер в той же транзакции.

В Prisma `workspaceId` старых моделей пока optional: старые DTO/сервисы по-прежнему пишут только `userId`. Перед INSERT/UPDATE триггер заполняет workspace, SQL CHECK не разрешает сохранить NULL. После перевода backend на явный workspace это поле можно сделать обязательным в Prisma и убрать переходную автоматику отдельной миграцией.

Триггеры запрещают неявный перенос старой записи другому владельцу и связывание сделки с заёмщиком/залогом другого workspace. В новых таблицах составные FK защищают связи договоров, участников, документов и обеспечения между кабинетами.

Существующие суммы, ставки, платежи и выдачи НЕ преобразуются автоматически в новый финансовый учёт. `contracts`, `loan_accounts`, `terms_versions` и `financial_events` из старых Deal/Payment/Disbursement не создаются: потребуется явная процедура при подключении backend, проверка единиц ставок и полноты истории. `Party.legacyBorrowerId` оставлен для однозначной связи при таком переносе.

До переключения backend старые таблицы — источник данных для текущих экранов. Нельзя одновременно использовать их и новые события как независимые источники остатка одного займа. Новые роли пока являются только моделью доступа: существующие маршруты продолжают фильтровать по userId; делегирование реализуется следующим этапом.

## Идентичности и роли

`WorkspaceRole` — уровень полномочий OWNER / ADMIN / MANAGER / VIEWER. Это не профессия пользователя. Роли инвестора, сопровождающего и брокера не записаны в глобальный user.role. Участие в конкретном договоре задаёт `ContractPartyRole`. `Party.userId` — место для будущего подтверждённого связывания участника с аккаунтом; одной записи в БД недостаточно для выдачи доступа заёмщику.

`loan_accounts` — расчётные счета, не банковские. Одному договору LOAN соответствует не более одного счёта в одной валюте. Договоры залога и агентские договоры сами по себе не создают расчётный счёт. Банковские ссылки пока могут передаваться через sourceSystem/sourceRef/sourceRevision события без FK к ещё не реализованным банковским таблицам.

## Финансовая история

Деньги — Decimal(20,2), ставки в строках начисления — Decimal(18,10), промежуточные результаты — Decimal(30,12). Дробная ставка 0.04 означает 4%; период DAY/MONTH/YEAR задаётся отдельно. Эти единицы нельзя автоматически приписывать существующим Deal.preferentialRate и другим legacy-полям.

Договорные дни хранятся как DATE, моменты получения данных — TIMESTAMPTZ(3). Часовой пояс хранится в версии календаря, а не берётся из настроек сервера. Каждый опубликованный набор условий — полный снимок. `effectiveOn` задаёт дату действия, `recordedAt` — момент публикации в системе. Допсоглашение не создаёт сумму выданного займа без отдельного события выдачи.

Публикация: создать DRAFT календарь, заполнить дни, опубликовать; создать DRAFT terms_version, заполнить правила, опубликовать. SQL запрещает менять/удалять опубликованные версии и их дочерние строки. Для terms обязательно наличие правил и опубликованного календаря. Формат JSON проверяется на object в БД; в backend ещё предстоит реализовать валидацию каждой версии схемы, полноты календаря, формул и канонических хешей. Публикация в БД сама по себе не подтверждает корректность или юридическую применимость условий.

Принятые `financial_events` неизменяемы. Основные денежные события содержат положительную amount, направление определяется kind; у NOTICE сумма отсутствует. Для исправления создаётся REVERSAL со ссылкой на исходное событие того же займа и той же суммой. Повторное полное сторно и сторно другого сторно запрещены. Частичное исправление: полное сторно + новое правильное событие в одной транзакции. `sequenceNo` задаёт уникальный порядок принятия в рамках займа, `idempotencyKey` защищает от повторной загрузки. Порядок финансовой обработки событий одного дня будет определять версия алгоритма.

## Выпуск расчёта

1. Создать `calculation_runs` со статусом RUNNING, датой расчёта, knowledgeCutoff, версией алгоритма и хешем полного входа.
2. Записать manifest в `calculation_inputs`: точные события, опубликованные условия и календари. SQL проверяет принадлежность займу, даты известных событий/условий и хеши версий. Хеш события и inputHash вычисляет и проверяет backend, не PostgreSQL.
3. Записать obligations, accrual_lines, payment_allocations и loan_snapshot.
4. Согласовать unpaidAmount с распределениями и завершить run статусом SUCCEEDED в транзакции. При ошибке — откат результатов/FAILED.

Окончательные run и их результаты неизменяемы. Историю запусков нельзя удалять; повторный расчёт создаёт новую запись. Составные FK запрещают смешивать займы, запуски и версии условий в распределениях. SQL ограничивает сумму распределения размером поступления и обязательства, сериализуя записи блокировкой owning run. Backend должен использовать короткие транзакции READ COMMITTED; при SERIALIZABLE повторять транзакцию при конфликте сериализации. REPEATABLE READ для параллельной записи одного run не является поддерживаемым режимом этого протокола.

Успешный run требует manifest и snapshot. Проверяется наличие использованных условий/календарей в manifest и соответствие unpaidAmount распределениям; нельзя использовать поступление, сторно которого включено во вход. Формулы, полнота всех применимых событий и числовое соответствие итогового snapshot — ответственность будущего расчётного ядра и его контрольных примеров.

Основное приложение читает итог только из SUCCEEDED runs; предварительные строки RUNNING не являются финансовым ответом. dueTotal включает overdueTotal, а principalOutstanding может содержать тело, срок возврата которого ещё не наступил. Неизвестная сумма досрочного возврата хранится как NULL с причиной в diagnostics.

## Команды из корня репозитория

```powershell
pnpm --dir apps/api db:validate
pnpm --dir apps/api db:generate
pnpm --dir apps/api db:status
pnpm --dir apps/api db:migrate
```

Команда db:migrate применяет существующие миграции через `migrate deploy`, без reset и без генерации миграций по живой базе. Конфигурация явно задана как prisma7.config.ts. `.env` загружается встроенным Node process.loadEnvFile; переданный извне DATABASE_URL имеет приоритет. Конфигурация проверена с установленным Node 24.16.0.

Не заменять применение миграций на `db push`: Prisma-схема не описывает SQL CHECK и триггеры. Следующие миграции генерировать через migrate diff/create-only с просмотром SQL; существующие применённые миграции не редактировать. Применение схемы не запускает backend-функции начисления.

## Интеграционная проверка миграции

```powershell
$env:TEST_DATABASE_URL='postgresql://USER:PASSWORD@127.0.0.1:5432/zaloghub_migration_test'
pnpm --dir apps/api test:db
```

Нужна отдельная локальная БД с точным именем `zaloghub_migration_test`, пользователь должен иметь право создавать схемы. Тест не загружает .env и не использует DATABASE_URL. Он создаёт собственную случайную схему, применяет предыдущие миграции, вставляет legacy-данные, применяет новую миграцию и проверяет их сохранность/ограничения. Собственная схема удаляется в finally; существующие таблицы не очищаются. При добавлении следующей миграции нужно обновить тестовую границу upgrade.

Дополнительно выполнены: применение цепочки миграций с нуля на отдельной PostgreSQL, schema diff, генерация Prisma Client и сборка NestJS. Финансовые формулы ещё не реализованы и этой проверкой не подтверждаются.

## Результат проверки этого этапа

- Миграция применена к локальной zaloghub; резервная копия до изменений сохранена в apps/api/.local/db-backups/ (не попадает в Git).
- Содержимое всех прежних таблиц сверено до/после по количеству записей и хешам содержимого; различий нет, кроме добавленного workspaceId.
- 37 интеграционных проверок миграции пройдены; чистая установка, Prisma validate, отсутствие schema drift и NestJS build подтверждены.
- В существующем наборе unit-тестов 13 прошли, 4 теста AuthService не прошли: старый mock конструктора не передаёт AuthChallengeService. Полная TypeScript-проверка тестовых исходников также обнаруживает этот старый двухаргументный вызов. Авторизация и её тесты в этом этапе не изменялись.
